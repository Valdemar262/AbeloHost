# AbeloHost Blog

Блог на чистом PHP, MySQL и Smarty, без фреймворков.

Реализованы окружение, маршрутизация, шаблоны, схема данных, миграции, сидинг, главная и страницы категорий с сортировкой и пагинацией. Страница статьи со счётчиком просмотров и похожими материалами — следующий этап; ссылки карточек на `/article/{slug}` пока возвращают 404.

## Требования

- Для Docker-запуска: Docker Engine / Docker Desktop / OrbStack и Docker Compose v2+.
- Для запуска без Docker: PHP 8.1+ с `PDO` и `pdo_mysql`, Composer 2, MySQL 8.x.

В Docker используется PHP 8.3 с Apache и MySQL 8.4. Образы PHP, Composer и MySQL закреплены digest; PHP-зависимости закреплены в `composer.lock`. `config.platform.php` ограничивает зависимости совместимостью с PHP 8.1. Образы и lock-файл следует обновлять осознанно, с повторной проверкой проекта.

## Быстрый старт с Docker

```bash
cp .env.example .env
docker compose up --build -d --wait
docker compose exec --user www-data app php bin/check-db.php
docker compose exec --user www-data app php bin/migrate.php
docker compose exec --user www-data app php bin/seed.php
```

Откройте [http://localhost:8080](http://localhost:8080). Успешная проверка БД выводит `MySQL connection OK (utf8mb4, UTC).` После миграций и сидинга в БД будут 5 категорий и 31 статья. Главная покажет 4 категории с опубликованными статьями; пустая категория и будущая публикация в неё не попадут.

Если порт занят, измените `APP_PORT` в `.env` и повторите `docker compose up -d --wait`. HTTP-порт доступен только на локальном интерфейсе; порт MySQL наружу не публикуется. Пример паролей предназначен для локальной разработки. Настоящий `.env` не включается в Git и образ приложения.

Исходники и Composer-зависимости копируются в образ при сборке. После изменения PHP, шаблонов или CSS пересоберите приложение:

```bash
docker compose up --build -d --wait
```

На хосте не нужны PHP и Composer. Для более быстрого редактирования без пересборок можно использовать локальный запуск ниже.

Полезные команды:

```bash
docker compose ps
docker compose logs app db
docker compose exec --user www-data app sh -c 'cat var/log/app.log'
docker compose stop
docker compose down
```

Файл `app.log` появляется после первой записанной ошибки. `docker compose down` сохраняет данные. Не добавляйте `-v`, если хотите сохранить БД: этот флаг удаляет volumes. Изменение паролей в `.env` не меняет учётные данные уже инициализированной MySQL — они задаются при первом создании БД.

## Запуск без Docker

Создайте в своей MySQL пустую БД `abelohost` с `utf8mb4` и отдельного пользователя с правами на эту БД. Затем:

```bash
composer install
export DB_HOST=127.0.0.1
export DB_PORT=3306
export DB_DATABASE=abelohost
export DB_USERNAME=blog
export DB_PASSWORD='your-local-password'
composer check-db
composer migrate
composer seed
composer serve
```

Приложение доступно на [http://127.0.0.1:8080](http://127.0.0.1:8080). Встроенный сервер PHP предназначен для локальной разработки. При другом порте используйте, например:

```bash
php -d display_errors=0 -S 127.0.0.1:8081 -t public public/router.php
```

PHP читает **переменные окружения**, а не файл `.env`. Docker Compose читает `.env` и передаёт нужные значения контейнерам; при локальном запуске используются команды `export`. В контейнере адрес БД всегда `db:3306`; переменные `DB_HOST`/`DB_PORT` в `.env.example` приведены как справочник для локальной конфигурации.

Для другого Apache/Nginx document root должен указывать на `public/`; запросы к отсутствующим файлам нужно направлять в `public/index.php`. Пользователь PHP должен иметь право создавать/изменять `var/`; не используйте права `777`. В Docker нужные каталоги и права создаются при сборке.

## Проверки

В Docker:

```bash
docker compose exec --user www-data app composer validate --strict
docker compose exec --user www-data app composer lint
docker compose exec --user www-data app composer test
docker compose exec --user www-data app composer test:http -- http://127.0.0.1
docker compose exec --user www-data app composer check-db
```

Без Docker, при запущенном `composer serve`:

```bash
composer validate --strict
composer lint
composer test
composer test:http
composer check-db
```

`composer test` проверяет маршрутизацию, параметры пути и запроса, Smarty, экранирование HTML и безопасный ответ 500 при сбое загрузки приложения. Сбой моделируется в отдельном временном каталоге и не меняет рабочие файлы. `composer test:http` требует запущенного приложения с миграциями и демонстрационными данными: проверяет главную, категории, сортировку, пагинацию, ответы 200/404/405, HEAD без тела, CSS и недоступность внутренних файлов. `composer check-db` выполняет `SELECT 1` через PDO; таблицы и данные не изменяются.

## Главная и категории

Главная `/` показывает категории по названию и до трёх последних опубликованных статей в каждой. Кнопка «Все статьи» ведёт на `/category/{slug}`. Пустые категории скрыты на главной, но доступны по прямой ссылке с сообщением об отсутствии публикаций.

На странице категории выводятся название, описание, общее количество статей и до 9 карточек. Параметр `sort=date` задаёт порядок по дате от новых к старым, `sort=views` — по просмотрам от большего к меньшему. При равных просмотрах сравнивается дата; при равных датах — ID по убыванию. Это делает порядок однозначным, пока данные не меняются.

Параметр `page` начинается с 1. Пагинация сохраняет выбранную сортировку; отправка формы сортировки возвращает к первой странице. Навигация показывает первую, последнюю и соседние страницы, чтобы число ссылок не росло вместе с количеством статей.

Примеры после сидинга:

- `/category/php` — первая страница, сначала новые.
- `/category/php?sort=views&page=2` — вторая страница, сначала популярные.
- `/category/notes` — существующая пустая категория.

Неизвестная категория и номер страницы за пределами списка возвращают 404. Некорректные значения `page` заменяются на 1, неизвестный `sort` — на `date`. В списки входят только статьи с `published_at` не позже текущего времени UTC; для подсчёта и выборки категории используется одна временная граница.

Главная получает данные одним запросом с `ROW_NUMBER()` по категориям, без отдельного запроса на каждую. Страница категории выполняет поиск категории, подсчёт статей и выборку с `LIMIT`/`OFFSET`. Полный текст статьи в карточки не загружается. Сортировка выбирается из двух заранее заданных SQL-выражений, значения передаются параметрами PDO.

## Схема и миграции

- `categories`: название, описание и уникальный slug.
- `posts`: изображение, заголовок, описание, текст, дата публикации, просмотры и уникальный slug.
- `post_category`: связь многие ко многим; первичный ключ исключает повторные связи.
- `schema_migrations`: имя SQL-файла, SHA-256, время начала и успешного применения.

Таблицы используют InnoDB и `utf8mb4`; slug хранится в ASCII с учётом регистра. Даты записываются в UTC. Индексы предусмотрены для порядка по дате и просмотрам, а также для поиска статей категории. Их доступность проверяется через `EXPLAIN`; выбор оптимизатора на небольшой демонстрационной БД не заменяет нагрузочную проверку.

Удаление статьи удаляет её связи. Удаление категории, на которую ссылаются статьи, запрещено внешним ключом. `PostRepository::create()` требует хотя бы одну категорию и сохраняет статью со связями атомарно. Если метод вызван внутри существующей транзакции, её завершает вызывающий код; сидер при любой ошибке откатывает всю свою транзакцию.

```bash
php bin/migrate.php
php bin/seed.php
```

В Docker эти команды выполняются через `docker compose exec --user www-data app`. Аналоги в Composer: `composer migrate` и `composer seed`.

Каждый файл `database/migrations/NNN_description.sql` содержит один SQL-запрос. Новые файлы добавляются после уже применённых; существующие не редактируются и не переименовываются. Повторный запуск пропускает применённые файлы, проверяя их контрольные суммы. Несколько SQL-запросов в одном вызове PDO запрещены.

DDL в MySQL делает неявный commit, поэтому мигратор не обещает откат схемы транзакцией. Перед выполнением файла он сохраняет запись с `applied_at = NULL`, после успеха отмечает время применения. Ошибка или аварийное завершение оставляет незавершённую запись, которая блокирует повторный запуск. Команда завершается с кодом 1 и именем проблемного файла.

При незавершённой миграции сначала сравните реальную схему с SQL-файлом. Если запрос не применился, устраните причину и удалите только его незавершённую запись из `schema_migrations` перед повтором. Если запрос уже применился, проверьте схему и контрольную сумму и отметьте эту запись как применённую. Автоматического сброса данных и rollback-команды нет. Такое поведение также учитывает остановку процесса между DDL и обновлением журнала.

Миграции и сидинг используют одну именованную блокировку MySQL для текущей базы: второй процесс ожидает до 10 секунд и при тайм-ауте завершается с ошибкой.

## Демонстрационные данные

Сидер добавляет 5 категорий, 30 опубликованных статей с фиксированными датами в январе 2025 года и одну будущую публикацию от 1 января 2099 года. В данных есть пустой раздел «Заметки», две статьи в «Интерфейсах», 14 опубликованных статей в PHP, пересекающиеся категории и совпадающие значения дат и просмотров. Изображения — локальные SVG в `public/assets/images/`, внешние сервисы не нужны.

Slug определяет, существует ли запись. Сидер **добавляет только отсутствующие записи**: не перезаписывает тексты, просмотры или связи существующих статей и не удаляет пользовательские данные. Изменение демонстрационного файла не обновляет уже созданную запись. Все вставки выполняются одной транзакцией; ошибка категории, изображения или SQL откатывает весь запуск. Сидинг запускается явно, после миграций, а не при каждом старте контейнера.

## Интеграционные проверки MySQL

```bash
docker compose -p abelohost-tests -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests
```

Команда собирает приложение и запускает отдельную MySQL без опубликованных портов и без рабочих volumes. Тестовые данные хранятся в `tmpfs` и исчезают при остановке контейнера. После завершения проверок Compose останавливает тестовую БД; команду можно запускать повторно. Удалить остановленные тестовые контейнеры можно так:

```bash
docker compose -p abelohost-tests -f compose.test.yaml down
```

Проверяются миграции и их повторный запуск, контрольные суммы, незавершённая миграция, конкурентный сидинг, сохранение существующих данных, откат транзакций, уникальность, внешние ключи, Unicode, просмотры и индексы. Проверки каталога дополнительно подтверждают один SELECT для главной, состав последних статей, обе сортировки, границы пагинации, пустые категории, исключение будущих публикаций и экранирование значений в шаблонах. Скрипт `composer test:database` допускает только **пустую** БД `abelohost_test` и отказывается работать с уже заполненной; для обычного запуска используйте изолированное окружение выше.

## Структура

```text
bin/check-db.php         проверка подключения к MySQL
bin/migrate.php          применение SQL-миграций
bin/seed.php             добавление демонстрационных данных
database/migrations/    последовательные изменения схемы
database/seeds/         данные для повторяемого сидинга
config/app.php           конфигурация из окружения
config/bootstrap.php     автозагрузка и инициализация Smarty
docker/                  PHP/Apache image и настройки сервера
public/index.php         вход в приложение
public/router.php        маршрутизатор встроенного PHP-сервера
public/assets/           публичные стили и изображения
src/Controller/          обработчики страниц
src/Database/            миграции, сидинг и блокировка CLI-команд
src/Repository/          SQL для категорий и статей
src/Http/                маршрутизация и HTTP-ответы
src/Database.php         создание PDO-соединения
src/View.php             настройка Smarty и рендеринг
templates/               общий layout, главная, категория и ошибки
templates/components/    карточка статьи и пагинация
tests/catalog.php        проверки списков и контроллеров на MySQL
tests/                   проверки каркаса, HTTP и интеграция с MySQL
var/                     автоматически создаваемые логи и файлы Smarty
```

Запрос проходит через `public/index.php`, маршрутизатор и контроллер. Маршрутизатор передаёт параметры пути и query string обработчику. `HomeController` готовит главную, `CategoryController` проверяет параметры сортировки и страницы и формирует пагинацию. Контроллеры возвращают HTTP-ответ с отрендеренным шаблоном; SQL находится в репозиториях. `PostRepository::findBySlug()` используется для внутренней работы и может вернуть будущую публикацию, а публичные методы выборки явно фильтруют дату. Соединение создаётся через `Database::connect()` в обработчике страницы. Главная и категории требуют доступной MySQL с применёнными миграциями; неизвестный маршрут и неподдерживаемый метод обрабатываются без подключения к БД.

Smarty экранирует переменные по умолчанию, кэширование HTML отключено. PDO использует `utf8mb4`, исключения и настоящие подготовленные запросы; часовой пояс PHP и сессии MySQL — UTC. Исключения записываются в `var/log/app.log`, а посетителю возвращается общая ошибка без stack trace. Если даже Smarty или Composer недоступны, предусмотрен простой резервный ответ 500.

Документация зависимостей: [Smarty](https://smarty-php.github.io/smarty/stable/), [официальный PHP Docker image](https://hub.docker.com/_/php).
